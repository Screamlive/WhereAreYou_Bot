# План изменений

## Текущий функционал

### Ролевая модель и состояния доступа
- Состояния пользователя:
  - **не зарегистрирован** — записи в `users` нет.
  - **ожидает одобрения** — `is_approved=0`.
  - **одобрен** — `is_approved=1`.
- Роли:
  - **пользователь** — `is_admin=0`.
  - **администратор** — `is_admin=1`.
- Доступ к функциям строится на проверках `is_approved` и `is_admin`.
- При нажатии «Отмена» в любом процессе FSM состояние сбрасывается и возвращается меню по роли.

### Регистрация и доступ
- `/start` показывает меню:
  - незарегистрированным — кнопку «Зарегистрироваться».
  - не одобренным — уведомление об ожидании.
  - одобренным — меню по роли.
- Регистрация через кнопку «Зарегистрироваться» + ввод ФИО.
- Админ одобряет/отклоняет заявки; первичный админ назначается вручную в БД.

### Пользователь (одобренный)
- Меню:
  - «Добавить отсутствие»
  - «Мои отсутствия»
  - «Добавить отсутствие другому сотруднику»
- **Добавить отсутствие**:
  - выбор категории (Отпуск/Больничный/DayOff/Другое),
  - ввод дат (дд.мм.гггг),
  - комментарий,
  - создается заявка со статусом `pending`,
  - админам отправляется уведомление с кнопками approve/decline.
- **Мои отсутствия**:
  - вывод всех заявок пользователя со статусом,
  - для `approved` отображаются кнопки «Удалить #ID» и «Изменить #ID».
- **Запрос на удаление** (только `approved`):
  - админам отправляется запрос на approve/decline,
  - при одобрении запись удаляется, пользователь получает уведомление.
- **Запрос на изменение** (только `approved`):
  - пользователь вводит новые значения,
  - создается запись в `edit_requests`,
  - админам отправляется сравнение старого/нового с approve/decline,
  - при одобрении заявка обновляется, пользователь получает уведомление.
- **Добавить отсутствие другому сотруднику**:
  - доступно любому одобренному пользователю,
  - выбор сотрудника из списка одобренных,
  - ввод категории/дат/комментария,
  - создается `pending`‑заявка на другого пользователя,
  - админы и целевой пользователь получают уведомления.

### Администратор
- Имеет весь функционал пользователя.
- **Управление пользователями**:
  - «Список запросов» (ожидающие одобрения) с inline approve/decline.
  - команды `/approve <id>` и `/decline <id>`.
  - «Список сотрудников» (одобренные).
  - «Назначить админом» / «Отозвать админа» / «Список админов».
  - «Удалить сотрудника» — удаляет пользователя и все его отсутствия (только не‑админов).
- **Управление отсутствиями**:
  - «Заявки на отсутствие» — список `pending` заявок с approve/decline.
  - «Посмотреть отсутствия сотрудника» — список всех заявок по выбранному пользователю.
  - «Удалить отсутствие сотрудника» — удаление любой заявки по выбранному пользователю.
  - «Добавить отсутствие» — как у пользователя (создается `pending`).
  - «Удалить мои отсутствия» — быстрый доступ к своим заявкам.
- **Выгрузки**:
  - CSV за период (с вводом дат).
  - список отсутствий за сегодня (пересечение даты today с периодами).

### Заявки и статусы
- Статусы: `pending` → `approved` / `declined`.
- Даты вводятся в формате `дд.мм.гггг`, сохраняются как ISO `YYYY-MM-DD`.

### Технически
- Хранилище: SQLite `bot_database.db`.
- Таблицы: `users`, `absences`, `logs`, `edit_requests`.
- Логирование действий в таблицу `logs` и в консоль.

## Новый функционал (планы)

### Новая ролевая модель и группы
- Ввести сущность **группа** (например, «отдел №1») и привязку пользователей к группам.
- Пользователь может состоять в **нескольких группах**.
- Роли:
  - **Суперадмин** (глобальная роль) — управляет группами и администраторами групп.
  - **Администратор группы** — управляет только своей группой.
  - **Пользователь** — принадлежит группе и работает внутри неё.
- Суперадмин:
  - создает/удаляет группы;
  - назначает администратора группы;
  - добавляет пользователей в группу;
  - удаляет пользователя из группы;
  - имеет доступ к глобальным спискам/выгрузкам (все группы).
  - может менять имя пользователя;
  - может смотреть username пользователя в формате `@username`.
  - пользователь получает уведомление при добавлении/удалении из группы.
- Администратор группы (в рамках своей группы):
  - принимает заявки на вступление в группу;
  - согласовывает заявки на отсутствие (pending);
  - удаляет/изменяет заявки на отсутствие;
  - добавляет отсутствие другим пользователям;
  - видит «отсутствия на сегодня» по своей группе;
  - выгружает CSV за период по своей группе;
  - удаляет сотрудников **из своей группы**;
  - просматривает список администраторов своей группы (без права изменения).
- Пользователь (в рамках своей группы):
  - добавляет отсутствие;
  - смотрит свои отсутствия;
  - смотрит список своих групп;
  - запрашивает удаление/изменение одобренных отсутствий;
  - добавляет отсутствие другому сотруднику (**между группами тоже**).

### Изменения бизнес‑логики
- Разделить:
  - **одобрение пользователя в боте** (глобально);
  - **вступление в конкретную группу** (внутри группы).
- Поток регистрации:
  - пользователь сначала **одобряется в боте**;
  - выбор группы — **сразу**;
  - далее админ группы **одобряет вступление** в выбранную группу.
- Суперадмину нужен функционал **распределения пользователей по группам**.
- Все админские операции должны фильтроваться по группе,
  кроме суперадмина (он видит всё).
- Отсутствие принадлежит **пользователю**, а не группе.
  Если пользователь состоит в нескольких группах, его отсутствие
  отображается **во всех** этих группах.
- Согласование отсутствий:
  - админ группы целевого пользователя;
  - суперадмин имеет право согласовывать любые отсутствия.
- Удаление сотрудника админом группы = удаление **членства в группе**,
  а не удаление пользователя из бота.
- Админ группы видит **только свою** группу.
- Выход пользователя из группы — **по согласованию** админа группы или суперадмина.
- Регистрация:
  - пользователь подает **заявку в одну группу**;
  - после регистрации можно подавать заявки в **дополнительные группы**.
- Если у пользователя **нет одобренной группы**, ему доступен только функционал
  подачи заявки в группу (прочие функции недоступны).
- Админы, состоящие в нескольких группах:
  - при входе выбирают **рабочую группу**;
  - меню и списки фильтруются по выбранной группе;
  - кнопка «Сменить группу» возвращает к выбору.
- Запоминать **последнюю выбранную группу** в БД и использовать как дефолт.
- «Добавить отсутствие другому сотруднику»:
  - доступна межгрупповая операция;
  - список пользователей — **полный**, во всех группах, **в алфавитном порядке**.

### Данные (ожидаемые изменения)
- Новая таблица `groups` (id, name, …).
- Связь **пользователь ↔ группа** через отдельную таблицу (many‑to‑many).
- Роль пользователя:
  - глобальная (`superadmin`) — в `users`;
  - роль в группе (`group_admin` / `member`) — в таблице связей.
- Сохранение последней выбранной группы админа (например, `users.last_group_id`).
- Таблица заявок на вступление в группу.
- При необходимости — хранить `group_id` у заявок на отсутствие (если пользователь в нескольких группах).
