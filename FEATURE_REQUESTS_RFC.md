# RFC: Пакет новых фич

## 1) Цель документа

Документ фиксирует новые фич-реквесты до начала разработки.
Цель: убрать неоднозначности, согласовать архитектурные решения и внедрять изменения небольшими безопасными итерациями.

Дата: 2026-02-13


## 2) Текущие архитектурные ограничения

- Глобальная роль `superadmin` реализована через `users.is_admin=1`.
- Роль в группе хранится в `group_memberships.role`, фактически используются:
  - `admin`
  - `member`
- Контроль доступа централизован в `core.py`, обработчики разделены по доменам:
  - `handlers/admin.py`
  - `handlers/groups.py`
  - `handlers/absences.py`
  - `handlers/menus.py`
- Ежедневные уведомления формируются в `notifications.py` и запускаются через systemd timer.


## 3) Область новых требований

### FR-1: Новая роль помощника администратора группы (только чтение)

Требование:
- Добавить роль с функционалом как у администратора группы, но без права изменений.
- Роль должна видеть заявки, состав группы, пересечения и прочую операционную информацию.
- Нельзя согласовывать/отклонять заявки и выполнять любые изменяющие действия.

Рекомендуемая модель:
- Добавить роль `viewer` в `group_memberships.role`.
- Текущие роли `admin` и `member` оставить без изменений.
- Ввести явную матрицу прав на уровне сервисной логики, а не только в отдельных хендлерах.
- Для интерфейса использовать короткое название роли: `Наблюдатель`.

Матрица прав (предложение):
- `viewer` может:
  - смотреть заявки на вступление/выход;
  - смотреть заявки на отсутствие;
  - смотреть список пользователей и админов группы;
  - смотреть отсутствия (на сегодня, списки, выгрузка CSV);
  - смотреть пересечения.
- `viewer` не может:
  - согласовывать/отклонять заявки;
  - добавлять/редактировать/удалять отсутствия для других;
  - удалять пользователей из группы;
  - менять роли;
  - создавать/удалять группы.

Архитектурные изменения:
- `core.py`:
  - добавить хелперы: `user_is_group_viewer_any`, `get_view_groups`, `get_group_scope`;
  - `scope` должен возвращать флаги возможностей (`can_read`, `can_write`).
- `db_repo.py`:
  - проверки ролей должны принимать `admin` и (где нужно только чтение) `viewer`.
- `keyboards.py`:
  - добавить отдельное меню viewer или переиспользовать меню админа группы с исключением write-действий.
- handlers:
  - явно проверять write-права в approve/decline/delete/update сценариях.

UX и пользовательские потоки (обязательные):
- Запрос роли пользователем:
  - в разделе `Группы` добавить кнопку `Запросить роль наблюдателя`;
  - пользователь выбирает группу, где уже состоит;
  - создается заявка на роль наблюдателя со статусом `pending`;
  - уведомление уходит администраторам выбранной группы и суперадминам.
- Назначение роли администраторами:
  - администратор группы и суперадмин могут назначить роль `Наблюдатель` вручную;
  - администратор группы действует только в рамках своей группы, суперадмин — в любой.
- Интерфейс после назначения:
  - после назначения пользователю отправляется уведомление:
    - в какую группу назначен;
    - какая роль назначена (`Наблюдатель`);
  - сразу после назначения выполняется автоматическое обновление меню (`TEXT_MENU_UPDATED` + новый `reply_markup`);
  - без перезапуска диалога и без ручного `/start`.
- Приоритет ролей в группе:
  - `admin` выше `viewer`;
  - при повышении до `admin` отдельная роль `viewer` не хранится;
  - при отзыве `admin` пользователь возвращается в `member`, если отдельно не назначен `viewer`.
- Меню роли `Наблюдатель`:
  - отображать только read-only разделы;
  - скрыть все кнопки, ведущие к изменяющим операциям.

Требуемое изменение БД для запроса роли:
- добавить таблицу `group_role_requests`:
  - `id PK`
  - `user_id`
  - `group_id`
  - `target_role` (`viewer`)
  - `status` (`pending`/`approved`/`declined`)
  - `requested_at`, `reviewed_at`
  - `requested_by`, `reviewed_by`

Декомпозиция реализации FR-1 (обязательный порядок):
1. Миграция БД:
   - расширить допустимые роли `group_memberships.role` значением `viewer`;
   - добавить `group_role_requests`.
2. Репозиторий (`db_repo.py`):
   - добавить операции для заявок на роль;
   - добавить проверки доступа `can_read_group`/`can_write_group` (или эквивалент).
3. Базовая ACL-логика (`core.py`):
   - добавить scope-логику с флагами чтение/изменение;
   - добавить определение роли `viewer` в группе.
4. Клавиатуры (`keyboards.py`):
   - добавить read-only меню `Наблюдатель`;
   - добавить кнопку запроса роли.
5. Хендлеры групп (`handlers/groups.py`):
   - реализовать пользовательский запрос роли;
   - реализовать обработку запроса админом группы/суперадмином;
   - реализовать ручное назначение роли админом группы/суперадмином.
6. Хендлеры отсутствий/админки:
   - разрешить read-only сценарии для `viewer`;
   - заблокировать все write-сценарии для `viewer`.
7. Уведомления и автообновление интерфейса:
   - отправка уведомления пользователю о назначении роли;
   - немедленное обновление меню после назначения/отзыва роли.
8. Тесты FR-1:
   - unit + flow + security cases по матрице прав.

Чек-лист приемки FR-1:
- [x] пользователь может подать запрос роли `Наблюдатель` в своей группе;
- [x] админ группы видит и обрабатывает запросы роли в своей группе;
- [x] суперадмин видит и обрабатывает запросы роли во всех группах;
- [x] после назначения пользователь получает уведомление и новое меню без `/start`;
- [x] `viewer` имеет доступ только к read-only функциям;
- [x] `viewer` не может approve/decline/delete/update;
- [x] при повышении `viewer -> admin` не возникает конфликтующих ролей;
- [x] тесты FR-1 зеленые.


### FR-2: Сервисная рассылка пользователям через консоль

Требование:
- Добавить рассылку через консоль (не через роль в боте).
- Использование: changelog, важные объявления по работе бота.

Рекомендуемая модель:
- Добавить скрипт `broadcast.py` как операционный инструмент.
- CLI-интерфейс:
  - `--audience all|approved|group:<id>|superadmins|group_admins`
  - `--text "..."` или `--file <path>`
  - `--dry-run`
  - `--limit N` (безопасная пакетная отправка)
- Отправка:
  - асинхронно, с throttling против flood limit;
  - логирование успехов/ошибок;
  - идемпотентность можно добавить вторым этапом.

Почему это решение:
- операционный контроль вне UI бота;
- безопасно для аварийных коммуникаций;
- не усложняет ролевую модель внутри интерфейса.


### FR-3: Настройки уведомлений для суперадминов по группам

Требование:
- Суперадмины, которые также администрируют группы, хотят в первую очередь получать уведомления по своим группам.
- Полный глобальный поток нужен как опциональный режим (замещение/форс-мажор).

Рекомендуемая модель:
- Добавить явные пользовательские настройки уведомлений (а не неявную логику по роли).
- Новые таблицы:
  - `superadmin_notification_prefs`:
    - `user_id PK`
    - `mode` из (`global`, `group_only`, `selected_groups`)
    - `updated_at`
  - `superadmin_notification_groups`:
    - `user_id`
    - `group_id`
    - PK (`user_id`, `group_id`)

Поведение:
- режим `global`: текущее поведение без изменений.
- режим `group_only`: только группы, где у пользователя есть роль в группе (`admin` или `viewer`, если назначен).
- режим `selected_groups`: только явно выбранные группы.

Формат пересечений:
- если режим не `global`, показывать пересечения только по релевантным группам;
- если `global`, оставлять текущий глобальный формат.

Точка управления:
- Целевое решение: управление через UI в разделе `Управление суперадминами`.
- В текущей реализации базовое переключение уже привязано к выбору скоупа суперадмином (`глобально` / выбранная группа).


### FR-4: Ускорить массовое добавление пользователей в группу

Требование:
- Сейчас для каждого пользователя нужно повторно запускать сценарий.
- Нужен быстрый массовый режим.

Варианты:
- Вариант A (минимальный): после добавления оставаться в том же состоянии и продолжать показывать список пользователей.
- Вариант B (рекомендуемый): множественный выбор с подтверждением.

Рекомендуемая модель (Вариант B):
- Шаг 1: выбрать группу.
- Шаг 2: постраничный список пользователей с переключателями:
  - `[ ] Иванов И.И.`
  - `[x] Петров П.П.`
- Управление:
  - `Готово`
  - `Сбросить выбор`
  - `Следующая/Предыдущая страница`
- После подтверждения:
  - добавить выбранных;
  - пропустить уже состоящих в группе;
  - показать итог: добавлено/пропущено/ошибки;
  - оставить сценарий активным до явного выхода.

Почему:
- лучший UX для 10+ пользователей;
- прозрачное состояние выбора;
- меньше случайных дублей.


### FR-5: Багфикс отображения длинных названий кнопок

Наблюдение:
- Длинные тексты в двухколоночных reply-кнопках визуально выглядят нецентрованными на части телефонов.

Важное ограничение:
- Финальный рендер и выравнивание контролирует Telegram-клиент.
- Сервер не может принудительно выставить центрирование текста.

Практическая стратегия исправления:
- сократить длинные подписи кнопок;
- не использовать две колонки для длинных названий;
- выносить длинные кнопки в одиночные строки;
- унифицировать длину формулировок в меню.

Правило реализации:
- максимальная длина подписи для двухколоночной строки: 20 символов (настраиваемо);
- если длиннее, кнопка переносится в отдельную строку.


## 4) Рекомендуемый порядок внедрения

Порядок:
1. FR-5 (нормализация текстов и раскладки клавиатур) - низкий риск, быстрый UX-эффект
2. FR-4 (массовое добавление пользователей) - рост производительности администрирования
3. FR-1 (роль viewer) - расширение ACL-модели
4. FR-3 (настройки уведомлений суперадмина) - расширение маршрутизации уведомлений
5. FR-2 (консольная рассылка) - операционный инструмент

Обоснование:
- сначала стабилизируем UX;
- затем улучшаем текущий болезненный поток;
- затем добавляем новую роль и контроль прав;
- затем расширяем уведомления;
- в конце добавляем отдельный сервисный инструмент рассылки.


## 5) Миграции БД

Планируемые миграции:
- `group_memberships.role`: добавить значение `viewer`;
- добавить таблицы настроек уведомлений суперадминов.

Требования к миграциям:
- идемпотентный SQL (безопасный повторный запуск);
- без деструктивных изменений;
- дефолт для существующих суперадминов: режим `global`.


## 6) Тестовая стратегия (обязательно)

Добавить/расширить тесты по каждой фиче:
- FR-1:
  - viewer имеет доступ к read-endpoint'ам;
  - viewer заблокирован на write-endpoint'ах.
- FR-2:
  - dry-run и реальная отправка;
  - корректность фильтрации аудиторий.
- FR-3:
  - маршрутизация по режимам (`global/group_only/selected_groups`);
  - корректная область пересечений в уведомлениях.
- FR-4:
  - корректность итогов multi-select (added/skipped/errors);
  - повторные добавления не создают дублей.
- FR-5:
  - проверка структуры клавиатур (длины/раскладки строк).

Обязательные условия регрессионного прогона:
- запускать полный набор тестов командой:
  - `./.venv/bin/python -m unittest discover -s tests`
- результат должен быть:
  - `OK`
  - `skipped=0`
- при любых скипах релиз/мердж запрещен до устранения причины.


## 7) Риски и меры

- Регрессии прав доступа:
  - мера: централизованные проверки прав + negative tests.
- Шум уведомлений:
  - мера: явные настройки с консервативными дефолтами.
- Ограничения Telegram при массовой рассылке:
  - мера: throttling и retry/backoff.
- Путаница в массовом добавлении:
  - мера: явный счетчик выбранных и итоговый отчет.


## 8) Принятые целевые решения

1. Название роли:
   - техническое значение: `viewer`;
   - пользовательское название в UI: `Наблюдатель`.
2. Права viewer на CSV:
   - разрешить выгрузку CSV (read-only).
3. Управление настройками уведомлений суперадмина:
   - на первом этапе только консольный сценарий.
4. UX массового добавления:
   - использовать Вариант B (multi-select с подтверждением).
5. UX по роли `Наблюдатель`:
   - добавить пользовательский запрос роли;
   - добавить назначение администратором группы и суперадмином;
   - после назначения всегда отправлять уведомление и сразу обновлять меню.

- архитектурные решения согласованы;

- реализация разбита на небольшие коммиты по фичам;
