## 1) Проблема

Проект функционально вырос, но структура остается «плоской»:
- смешаны точки входа, бизнес-логика, доступ к БД и инфраструктурные детали;
- сложно безопасно вносить изменения без регрессий;
- увеличивается стоимость онбординга и поддержки;
- архитектурные границы неочевидны (где доменная логика, где слой данных, где orchestration).

## 2) Цель

Сделать структуру проекта предсказуемой и масштабируемой без потери стабильности:
- разделить слои (entrypoints / application / domain / data / infrastructure);
- оставить текущий UX/API без функциональных изменений на первых этапах;
- снизить риск регрессий через итерационный рефакторинг и обязательные тесты.

## 3) Non-goals

- не переписывать бота «с нуля»;
- не менять ролевую модель в рамках этого RFC;
- не менять бизнес-правила, если это не нужно для декомпозиции.

## 4) Принципы

1. **Малые итерации**: каждое изменение должно быть ограниченным и проверяемым.
2. **Совместимость**: текущие команды запуска (`python bot.py`, `python webapp_api.py`) сохраняются.
3. **No big-bang**: миграция модулей по слоям, без массового одномоментного переезда.
4. **Тест-гейт обязателен**: `./scripts/security_gate.sh` + полный набор тестов без skip.
5. **Ручной smoke после каждой итерации** на тестовом стенде.

## 5) Целевая структура (ориентир)

## 6) План внедрения

### Итерация R1 — Каркас без изменения поведения

- создать пакетную структуру `app/` и базовые подпакеты;
- перенести `settings.py` в пакетный слой (или оставить shim для совместимости);
- оставить root-entrypoints (`bot.py`, `webapp_api.py`, `notifications.py`, `broadcast.py`) как тонкие обертки.

Критерии приемки:
- все текущие команды запуска работают как раньше;
- тесты зеленые;
- нет функциональных изменений.

### Итерация R2 — Разделение entrypoints и orchestration

- вынести сборку приложения (инициализация bot/router/webapp) из root-файлов в `app/entrypoints/*`;
- убрать прямую инфраструктурную логику из модулей обработчиков.

Критерии приемки:
- поведение бота/WebApp идентично;
- проще читается путь выполнения «старт -> зависимости -> роутеры».

### Итерация R3 — Чистка слоя данных

- декомпозировать `db_repo.py` на тематические репозитории;
- выделить модуль подключения/инициализации БД;
- зафиксировать правило: бизнес-правила не живут в SQL-слое.

Критерии приемки:
- API репозиториев покрыто тестами;
- SQL/DB операции изолированы и переиспользуемы.

### Итерация R4 — Доменная логика и use-cases

- вынести доменные правила (ACL, валидации, сценарии согласования) в отдельные сервисы/use-cases;
- оставить handlers/web endpoints максимально тонкими (I/O + вызов use-case).

Критерии приемки:
- handlers перестают быть «монолитами»;
- ключевые бизнес-сценарии тестируются без Telegram/Aiohttp окружения.

### Итерация R5 — Консолидация WebApp-слоя

- разделить WebApp на auth/validation/service/export модули;
- унифицировать обработку ошибок и DTO-форматы;
- закрепить контракт API и тесты на регрессии.

Критерии приемки:
- WebApp-код структурно отделен от Telegram-бота;
- все WebApp security тесты и smoke проходят.

### Итерация R6 — Финализация и документирование

- обновить README/DOCUMENTATION под новую структуру;
- зафиксировать карту модулей и правила разработки;
- удалить устаревшие compatibility shims (если безопасно).

Критерии приемки:
- документация соответствует коду;
- структура понятна новому разработчику «с нуля».

## 7) Тестовая стратегия

После **каждой** итерации:
1. `./scripts/security_gate.sh`
2. `./.venv/bin/python -m unittest discover -s tests`
3. Ручной smoke:
   - запуск `bot.py`;
   - запуск `webapp_api.py`;
   - базовый пользовательский сценарий (вход, меню, заявка/просмотр).

Запрещено:
- merge с красным тестовым набором;
- skip тестов для «временного прохода».

## 8) Риски и снижение рисков

Риски:
- скрытые регрессии из-за перемещения модулей;
- циклические импорты при промежуточном состоянии;
- рост времени на миграцию.

Меры:
- миграция по слоям, а не по файлам «вразнобой»;
- compatibility wrappers на переходном этапе;
- обязательный тест-гейт и ручной smoke.

## 9) Политика коммитов для рефакторинга

- один коммит = одна логическая подзадача;
- сообщения на русском, кратко и по сути;
- в коммите явно фиксируется: «без изменения функционала», если это структурный шаг.

## 11) Вывод

Рефакторинг структуры целесообразен и должен идти итерациями без функциональных скачков.
Приоритет — стабильность, тестируемость и прозрачная поддержка проекта в долгую.
