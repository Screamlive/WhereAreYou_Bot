## 1) Цель

Снизить двойной ввод и зависимость от сторонних инструментов за счет встроенной
визуализации пересечений отсутствий внутри продукта, без изменения текущих
процессов согласования в Telegram-боте.

Ключевой принцип: WebApp в Telegram внедряется как дополнение (read-only), а не
как замена текущего интерфейса бота.

## 2) Что входит в V1 (обязательный scope)

1. Визуализация пересечений с точными датами по каждому сотруднику.
2. Просмотр пересечений:
   - глобально (только суперадмин);
   - по группе;
   - только по сотрудникам с ролью суперадмина.
3. Доступ:
   - суперадмин: все режимы + фильтры;
   - админ группы: только свои группы;
   - сотрудник: только свои группы (для планирования отпусков).
4. Период по умолчанию: весь текущий календарный год (`01.01.YYYY–31.12.YYYY`).
5. Цветовая дифференциация категорий отсутствий.
6. Мобильный UX:
   - фиксированная левая колонка с ФИО;
   - горизонтальный скролл таймлайна вправо/влево;
   - читабельные строки и легенда.
7. По клику на отсутствие: карточка с деталями и комментарием.

## 3) Что не входит в V1

- Любые операции изменения данных (approve/decline/edit/delete/create).
- Интеграции с внешними системами (Confluence и т.д.).
- Полная замена чат-интерфейса бота.

## 4) Роли и доступ (ACL)

### Суперадмин
- Видит:
  - глобальный срез;
  - любую отдельную группу;
  - отдельный срез «Только суперадмины».
- Может применять все read-only фильтры.

### Администратор группы
- Видит только группы, где у него роль `admin`.
- Не видит глобальный срез и чужие группы.

### Сотрудник
- Видит только группы, где состоит (`member`/`viewer`/`admin`).
- Не видит глобальный срез и чужие группы.

## 5) Бизнес-правила визуализации

1. Пересечение определяется стандартно: диапазоны дат пересекаются, если
   `start_a <= end_b` и `start_b <= end_a`.
2. В визуализации показываются отсутствия за выбранный год.
3. Статусы по умолчанию: `approved` + `pending` (с отдельной меткой статуса).
4. Отображаемые категории:
   - `vacation` (Отпуск)
   - `sick` (Больничный)
   - `dayoff`
   - `other`
5. Комментарий показывается в карточке отсутствия по клику.

## 6) UX/UI (read-only WebApp)

## 6.1 Экран «Пересечения»

Верхняя панель фильтров:
- Scope: `Глобально` / `Группа` / `Суперадмины` (набор зависит от роли).
- Выбор группы (если доступно несколько).
- Год (по умолчанию текущий).
- Чекбоксы статусов (`approved`, `pending`, `declined`).
- Фильтр категории.
- Поиск по ФИО/username.

Основная область:
- Таблица в стиле timeline (Gantt-подобная):
  - слева фиксированная колонка: ФИО + `@username`;
  - справа шкала месяцев/дней с горизонтальным скроллом;
  - на строке сотрудника — цветные интервалы отсутствий.
- Визуальные элементы:
  - легенда цветов категорий;
  - вертикальный маркер «сегодня»;
  - контрастная сетка выходных/будней.

Карточка по клику на интервал:
- ФИО, `@username`;
- категория;
- точные даты начала/окончания;
- статус;
- комментарий.

## 6.2 Цвета (базовая схема)

- `vacation`: синий
- `sick`: красный
- `dayoff`: оранжевый
- `other`: серый

Требования:
- контраст не ниже WCAG AA;
- дублирование цвета текстовой меткой категории (для color-blind случаев).

## 7) Техническая реализация

## 7.1 Архитектура

- Bot API: остается текущим.
- WebApp: отдельный read-only UI, открывается кнопкой из бота.
- Backend:
  - reuse текущей БД SQLite и репозиторного слоя;
  - отдельные read-only endpoints для WebApp.
- Ingress:
  - публичный HTTPS домен на Nginx reverse proxy;
  - проксирование в `webapp_api.py` на локальном порту (например `127.0.0.1:8080`);
  - разделение тест/прод по разным поддоменам.

## 7.2 Аутентификация

- Использовать Telegram WebApp `initData`.
- На сервере проверять подпись `initData`.
- После валидации вычислять роль и разрешенные scope.

## 7.3 Минимальные endpoint'ы

- `GET /webapp/v1/me` — профиль, роль, доступные scope/группы.
- `GET /webapp/v1/overlaps` — данные таймлайна по фильтрам:
  - `scope_type=global|group|superadmins`
  - `group_id` (если `scope_type=group`)
  - `year`
  - `statuses[]`
  - `categories[]`
  - `q` (поиск)
- `GET /webapp/v1/absence/{id}` — подробности интервала (включая комментарий).

## 7.4 Производительность

- Запрашивать данные только за выбранный год.
- Добавить/проверить индексы:
  - `absences(user_id, start_date, end_date, status)`
  - `group_memberships(group_id, user_id, role)`
- Пагинация/виртуализация строк при больших группах.

## 7.5 Публикация WebApp и безопасность доступа

- WebApp размещается на **публичном HTTPS URL** (требование Telegram WebApp).
- URL технически может быть открыт напрямую из браузера, это нормально.
- Доступ к данным должен выдаваться только после проверки подписи Telegram
  `initData` на backend.
- Запросы без валидного `initData` возвращают `401/403` (данные не выдаются).
- Dev fallback по `X-Telegram-User-Id` допускается только для локальной
  разработки и должен быть выключен в production.
- Входная точка для пользователей — кнопка WebApp в меню бота.

Production checklist:
- настроить публичный HTTPS домен;
- прописать домен в BotFather (`/setdomain`);
- включить initData-only режим (без dev fallback);
- настроить Nginx reverse proxy для маршрутов `/webapp`, `/webapp/static/`, `/webapp/v1/`;
- проверить, что прямой открытый URL без `initData` не раскрывает данные.

## 8) Риски и ограничения

- На мобильных маленький экран: решается фиксированной колонкой ФИО и скроллом.
- Большие выборки (глобальный режим): нужен лимит/ленивая отрисовка.
- Чувствительность комментариев: требуется единое правило видимости по ролям.

## 9) Зафиксированные best practices

Ниже зафиксирован целевой набор, который включается в план внедрения:

1. Быстрые пресеты периода: `Текущий год`, `Текущий месяц`, `Следующие 90 дней`.
2. Кнопка `Сегодня` (быстрый скролл к текущей дате).
3. Плотность отображения:
   - `Компактно` (меньше высота строк),
   - `Подробно` (лучше читаемость на телефоне).
4. Подсветка конфликтных дней (когда отсутствуют >= N сотрудников в один день).
5. Экспорт текущего вида в XLSX (read-only, без изменения данных).

Разбиение по релизам:
- V1 (обязательное): пункты 1-3;
- V1.1 (после стабилизации V1): пункты 4-5.

## 10) План внедрения по итерациям

### Итерация 1: Контракты и read-only backend
- Добавить read-only API-контракты (`/me`, `/overlaps`, `/absence/{id}`).
- Реализовать ACL-проверки по ролям для scope (`global/group/superadmins`).
- Добавить unit-тесты на ACL и фильтрацию данных.
- Результат: API готово, UI можно разрабатывать параллельно.

### Итерация 2: Базовый WebApp-экран пересечений
- Реализовать экран таймлайна на текущий год.
- Сделать фиксированную колонку ФИО/username и горизонтальный скролл.
- Реализовать цвета категорий и легенду.
- Результат: рабочая визуализация без расширенных фильтров.

### Итерация 3: Фильтры и карточка интервала
- Добавить фильтры: scope, группа, статусы, категории, поиск.
- Добавить клик по интервалу и карточку деталей (даты, статус, комментарий).
- Довести поведение по ролям:
  - суперадмин: глобально/группы/суперадмины;
  - админ/сотрудник: только доступные группы.
- Результат: полный обязательный функционал из исходного запроса.

### Итерация 4: Best practices V1
- Добавить пресеты периода (`год/месяц/90 дней`).
- Добавить кнопку `Сегодня`.
- Добавить переключатель плотности (`Компактно`/`Подробно`).
- Результат: улучшенная usability-версия V1.

### Итерация 5: Best practices V1.1
- Добавить подсветку дней с повышенной нагрузкой (конфликтные дни).
- Добавить экспорт текущего вида (XLSX, read-only).
- Добавить тесты на корректность экспорта и фильтров при экспорте.
- Результат: аналитический слой и удобный share/reporting.

### Итерация 6: Стабилизация и релиз
- Оптимизировать запросы и отрисовку под группы 50-200+ пользователей.
- Прогнать полный регрессионный набор тестов проекта.
- Провести ручной UX-проход на телефоне и desktop.
- Результат: готовность к production rollout.
